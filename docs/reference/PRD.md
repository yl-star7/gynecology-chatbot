# 부인과 상담 서비스 PRD

## 1. 문서 목적
이 문서는 부인과 상담 서비스의 제품 범위와 운영 범위를 확정하기 위한 기준 문서다. 현재 존재하는 코드 구조나 임시 구현 상태는 본 문서의 기준이 아니며, 본 문서를 기준으로 이후 정보구조, UX, API, 관리자 기능을 정리한다.

### 1.1 작성 전제
- 본 PRD는 현재 저장소의 기존 구현을 이어받는 문서가 아니다.
- 본 PRD는 "지금 시점에서 새 브랜치에서 다시 시작한다"는 가정으로 작성한다.
- 구현 기준 백엔드는 Supabase로 통일한다.
- 이후 설계, IA, API, 데이터 모델, 관리자 화면 정의는 이 PRD만 기준으로 가져간다.
- 구현 계획서나 기존 UI 초안보다 본 PRD의 범위 정의가 우선한다.

## 2. 제품 정의

### 2.1 제품 한 줄 정의
임산부와 가임기 사용자가 모바일 앱에서 안전한 상담, 감정 기록, 건강 기록 아카이빙을 수행하고, 운영자는 웹 관리자에서 사용자 운영과 콘텐츠 관리를 수행하는 상담 지원 서비스.

### 2.2 채널 분리 원칙
- 웹사이트는 관리자 뷰 전용이다.
- 모바일 앱은 사용자 뷰 전용이다.
- 사용자용 채팅, 캘린더, 로그인, 온보딩은 앱에만 제공한다.
- 관리자용 모니터링, 계정 복구, 콘텐츠 운영, 문서 관리, 로그 조회는 웹에만 제공한다.
- 웹과 앱은 같은 화면을 공유하는 방식이 아니라 관심사와 배포 단위를 분리한다.

### 2.3 기술 방향 원칙
- 백엔드와 데이터 저장소의 중심은 Supabase다.
- 인증, 사용자 데이터, 상담 데이터, 캘린더 로그, 관리자 운영 로그는 Supabase 기준으로 설계한다.
- 프론트엔드 기술 선택은 추후 조정 가능하지만 PRD의 제품 책임 분리는 고정한다.

### 2.4 목표
- 사용자가 반복 로그인 부담 없이 앱에서 상담을 이어갈 수 있어야 한다.
- 상담 내용을 날짜 기준으로 다시 볼 수 있어야 한다.
- 운영자가 사용자 계정 이슈를 직접 해결할 수 있어야 한다.
- 운영자가 상담 품질, 사용량, 콘텐츠를 웹 관리자에서 관리할 수 있어야 한다.
- 앱 배포 이후 비개발 운영자도 테스트 배포와 스토어 운영 절차를 따라갈 수 있어야 한다.

### 2.5 비목표
- 일반 사용자용 웹 채팅 서비스 제공
- 병원 EMR 연동
- 실시간 진료 예약/결제
- 의사-환자 양방향 라이브 상담
- 병원 전용 다중 테넌트 SaaS

## 3. 사용자와 역할

### 3.1 사용자 앱 사용자
- 임산부 또는 가임기 사용자
- 모바일 앱에서 회원가입, 로그인, 채팅, 감정 기록, 캘린더 조회를 수행

### 3.2 운영 관리자
- 서비스 운영 담당자
- 웹 관리자에서 사용자 현황 조회, 계정 수정, 비밀번호 재설정, 콘텐츠 관리, 대화 로그 조회, 문서 운영을 수행

### 3.3 슈퍼 관리자

- 관리자 생성/비활성화, 고위험 계정 작업 감사 확인 수행

## 4. 핵심 시나리오

### 4.1 사용자 첫 가입
1. 사용자가 앱을 설치하고 휴대폰 번호를 입력한다.
2. 휴대폰 본인인증을 1회 수행한다.
3. 인증 성공 후 사용자가 직접 비밀번호를 설정한다.
4. 계정 생성이 완료되고 앱 온보딩으로 진입한다.

### 4.2 사용자 재로그인
1. 사용자는 전화번호를 ID로 입력한다.
2. 사용자가 설정한 비밀번호를 입력한다.
3. 로그인 성공 시 이전 상담 상태와 저장 기록을 이어서 확인한다.

### 4.3 상담 중 기록 저장
1. 사용자가 AI 답변 또는 상담 요약을 저장한다.
2. 기본 연결 단위는 개별 메시지보다 채팅 세션이다.
3. 저장 시 해당 날짜의 앱 내 캘린더에 기록이 생성된다.
4. 사용자는 캘린더에서 날짜별로 기록을 다시 열람한다.

### 4.4 관리자 계정 복구 대응
1. 사용자가 전화번호 변경 또는 비밀번호 분실을 문의한다.
2. 관리자가 웹 관리자에서 사용자를 검색한다.
3. 관리자가 전화번호 변경, 로그인 ID 정정, 비밀번호 재설정 중 필요한 작업을 수행한다.
4. 모든 작업은 감사 로그로 남는다.

### 4.5 운영자 테스트 배포
1. 운영자가 앱 빌드 결과물을 확인한다.
2. 운영 문서를 따라 Apple TestFlight 또는 Google Play 테스트 트랙에 등록한다.
3. 테스터 초대와 스토어 가입 절차를 문서 기준으로 수행한다.

## 5. 기능 범위

### 5.1 사용자 앱

#### 5.1.1 인증
- 최초 1회 휴대폰 본인인증 필수
- 본인인증 직후 사용자 비밀번호 설정
- 이후 로그인은 전화번호 + 비밀번호 방식
- 자동 로그인 또는 세션 유지 지원
- 비밀번호 재설정 진입 경로 제공

#### 5.1.1.a 휴대폰 인증 3단계 구조

1. `mock`
- 개발용 단계
- 실제 문자 발송 없음
- 인증 코드 입력 UI와 서버 검증 인터페이스만 유지
- 로컬/스테이징 화면 개발, QA 흐름 확인 목적

2. `sms_otp`
- 실서비스 기본 단계
- SMS 발송 벤더를 통해 OTP 전송
- 사용자는 발송된 코드를 입력해 인증
- Supabase Auth Hook 또는 커스텀 OTP 테이블/검증 로직을 사용
- 한국 서비스 우선이면 Solapi 같은 국내 벤더를 우선 검토

3. `identity_verification`
- 고신뢰 본인확인 단계
- 단순 OTP가 아니라 통신사/실명 기반 본인확인 서비스 사용
- 계정 복구, 고위험 작업, 민감 기능 접근 시 추가 단계로 사용 가능
- MVP 필수 범위는 아니며 후속 확장 범위

#### 5.1.1.b 인증 단계별 적용 원칙
- 개발과 초기 QA는 `mock` 허용
- 운영 배포 전에는 최소 `sms_otp` 필수
- `identity_verification`은 규제, 민감도, 악용 리스크에 따라 선택 도입
- 앱 로그인 기본 식별자는 항상 전화번호다
- 비밀번호는 서버에 평문 저장하지 않고 해시로만 저장한다

#### 5.1.2 온보딩
- 임신 여부, 임신 주차 또는 예정일 등 최소 프로필 수집
- 사용 목적과 상담 톤 선호 수집
- 온보딩 완료 전 핵심 기능 진입 제한 가능

#### 5.1.3 AI 상담
- 사용자가 자유 입력 또는 추천 질문으로 상담 시작
- 채팅은 ChatGPT와 유사한 세션 단위로 관리
- 임신 주차, 저장된 맥락, 최근 감정 기록을 참고한 응답
- 위험 신호 질문에는 주의 문구와 내원 권고 기준 포함
- 의료 참고 근거 또는 출처 보기 제공
- 임신 주차별 RAG 지식 문서를 참고할 수 있어야 함

#### 5.1.4 상담 저장과 캘린더
- 사용자가 특정 상담 답변을 저장할 수 있어야 함
- 캘린더 기록은 기본적으로 `session_id`를 참조하고, 특정 저장 메시지가 필요한 경우에만 `message_id`를 추가로 참조
- 저장된 항목은 날짜 단위로 앱 캘린더에 노출
- 캘린더에서 일자별 기록 목록, 요약, 원문 이동 제공
- 기록 유형 예시:
  - 상담 저장
  - 증상 메모
  - AI 요약
  - 감정 체크인

#### 5.1.5 감정 기록
- 하루 단위 감정 상태 기록
- 감정 선택과 간단 메모 지원
- 캘린더와 연동 가능

#### 5.1.6 내 기록 내보내기
- 사용자가 자신의 기록을 다운로드 또는 공유 가능한 형태로 백업
- 민감 정보 포함 여부를 선택할 수 있어야 함

### 5.2 관리자 웹

#### 5.2.1 관리자 인증
- 관리자 전용 로그인 화면 제공
- 사용자 인증 체계와 분리
- 권한 수준에 따라 접근 메뉴 제어
- `admin`, `super_admin` 두 단계를 기본 role로 사용
- super_admin만 가능한 고위험 기능은 별도 보호

#### 5.2.2 대시보드
- 활성 사용자 수
- 일간/주간 로그인 수
- 일간 채팅량
- 감정 기록 추이
- 주요 운영 알림

#### 5.2.3 사용자 운영
- 사용자 검색
- 사용자 프로필 조회
- 전화번호 변경
- 로그인 ID 정정
- 비밀번호 재설정 또는 초기화
- 계정 상태 변경
- 최근 로그인/활동 확인

#### 5.2.4 상담 및 기록 조회
- 사용자별 상담 이력 조회
- 날짜별 저장 기록 조회
- 캘린더 저장 로그 확인
- 품질 관리 목적의 상담 샘플 검토

#### 5.2.5 콘텐츠 운영
- 카드뉴스/설문/안내 콘텐츠 등록, 수정, 비활성화
- AI 참고 문서 업로드 및 반영 상태 확인
- 캐릭터/톤 관련 리소스 관리

#### 5.2.6 감사와 운영 로그
- 계정 복구 작업 로그
- 관리자 액션 로그
- 실패한 운영 작업 로그

### 5.3 운영 문서
- Apple App Store 가입 안내
- Google Play Console 가입 안내
- TestFlight 테스터 등록 절차
- Google Play 내부/비공개 테스트 등록 절차
- 빌드 수령 후 운영자가 수행할 체크리스트
- 자주 발생하는 배포/테스터 초대 이슈 대응 가이드

## 6. UX 원칙

### 6.1 사용자 앱 UX
- 불안감을 높이지 않는 차분한 톤 사용
- 입력 부담을 줄이기 위해 추천 질문과 빠른 선택지 제공
- 저장과 다시보기 동선을 단순하게 유지
- 로그인은 최초 설정 이후 반복 OTP를 요구하지 않음

### 6.2 관리자 웹 UX
- 검색, 필터, 상태 요약이 빠르게 보여야 함
- 사용자 계정 수정 액션은 확인 절차와 로그를 남겨야 함
- 운영 요구가 늘어나도 메뉴와 모듈을 확장하기 쉬운 구조여야 함

## 7. 데이터 요구사항

### 7.0 데이터 설계 원칙
- 사용자 앱과 관리자 웹은 같은 Supabase 프로젝트의 공통 데이터를 사용한다.
- 사용자 권한과 관리자 권한은 분리된 접근 정책으로 제어한다.
- 계정 복구, 관리자 수정, 민감 데이터 조회는 모두 감사 가능해야 한다.

### 7.1 사용자 계정
- 사용자 고유 ID
- 전화번호
- 비밀번호 해시
- 최초 인증 시각
- 최근 로그인 시각
- 계정 상태

### 7.2 사용자 프로필
- 임신 상태
- 임신 주차 또는 예정일
- 온보딩 응답
- 선호 상담 톤

### 7.3 상담 데이터
- 대화 세션
- 메시지 이력
- 저장된 답변
- 감정 기록
- 캘린더 로그
- 임신 주차별 RAG 지식 문서

### 7.4 운영 데이터
- 관리자 액션 로그
- 계정 복구 감사 로그
- 콘텐츠 변경 이력

## 8. 관리자 계정 복구 정책
- 관리자는 사용자 전화번호를 변경할 수 있어야 한다.
- 관리자는 사용자 로그인 ID를 정정할 수 있어야 한다.
- 관리자는 사용자의 비밀번호 재설정 또는 초기화를 수행할 수 있어야 한다.
- 모든 계정 복구 작업은 누가, 언제, 무엇을, 왜 변경했는지 기록해야 한다.
- 고위험 작업은 상위 관리자 검토 절차를 둘 수 있다.
- 관리자 계정(role 변경, 관리자 생성/비활성화)은 super_admin만 수행한다.

## 9. 캘린더 기능 상세

### 9.1 목적
상담 내용을 일회성 채팅에서 끝내지 않고 날짜 기준 건강 기록으로 재사용하게 한다.

### 9.2 사용자 가치
- 언제 어떤 증상과 상담을 했는지 다시 확인 가능
- 감정 변화와 상담 흐름을 시간축으로 볼 수 있음
- 병원 방문 전 메모 정리에 활용 가능

### 9.3 최소 기능
- 월간 캘린더 뷰
- 특정 날짜 선택
- 날짜별 저장 기록 리스트
- 기록 상세 보기
- 원문 채팅으로 돌아가기

### 9.4 확장 가능 기능
- 증상 태그 필터
- 병원 방문 메모
- 알림 일정 연결
- 외부 캘린더 내보내기

## 10. 안전과 규제 관점
- 진단 확정 표현 금지
- 응급/위험 신호는 즉시 진료 권고 안내
- 민감정보는 관리자 권한과 로그 기준으로 제한 조회
- 관리자 화면은 사용자용 공개 링크가 없어야 함
- Supabase 권한 설계는 사용자용 데이터 접근과 관리자용 운영 접근을 분리해야 함

## 11. 성공 지표
- 가입 완료율
- 최초 인증 후 비밀번호 설정 완료율
- 재로그인 성공률
- 상담 저장 사용률
- 캘린더 재방문율
- 관리자 계정 복구 처리 시간
- 테스트 배포 운영 문서만으로 테스터 등록 완료 가능 여부

## 12. 범위 밖 항목
- 병원별 커스터마이징 포털
- 의사 직접 답변 라우팅
- 결제/구독 과금 체계
- 웹 사용자 버전 공개
- 다국어 운영

## 13. 수용 기준

### 13.1 사용자 앱
- 사용자는 최초 1회 휴대폰 인증 후 비밀번호를 설정할 수 있어야 한다.
- 사용자는 이후 전화번호와 비밀번호로 로그인할 수 있어야 한다.
- 사용자는 상담 내용을 저장하고 앱 내 캘린더에서 다시 열람할 수 있어야 한다.
- 사용자는 날짜별 기록 상세와 원문 이동 동선을 사용할 수 있어야 한다.

### 13.2 관리자 웹
- 관리자는 웹에서만 로그인 가능해야 한다.
- 관리자는 사용자 검색 후 전화번호 변경, 로그인 ID 정정, 비밀번호 재설정을 수행할 수 있어야 한다.
- 관리자의 계정 복구 작업은 감사 로그에 남아야 한다.
- 관리자는 대시보드에서 로그인/채팅/감정 기록 요약을 볼 수 있어야 한다.

### 13.3 운영 문서
- 운영 문서만 보고 Apple/Google 스토어 가입 절차를 이해할 수 있어야 한다.
- 운영 문서만 보고 TestFlight 또는 Google Play 테스트 등록을 진행할 수 있어야 한다.
