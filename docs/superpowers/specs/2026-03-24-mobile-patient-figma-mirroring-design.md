# 모바일 환자 흐름 Figma 이관 및 웹 미러링 설계

## 목적

환자용 경험의 기준 원본을 `apps/mobile`로 재정의하고, 주어진 Figma Make 구조를 기준으로 환자용 핵심 흐름 전체를 재편한다. 이후 `apps/web`의 모바일 웹 화면은 모바일 앱의 정보 구조와 화면 책임을 미러링하는 방식으로 따라간다.

이번 작업의 기준은 기존 화면을 부분 보정하는 것이 아니라, 모바일 환자 경험을 Figma 기준으로 사실상 새 구조로 엎는 것이다. 다만 세션, API, 저장 포트, 런타임 인프라는 최대한 재사용한다.

## 범위

포함:

- `apps/mobile` 환자용 홈 흐름
- `apps/mobile` 환자용 오늘,우리 대화 허브
- `apps/mobile` 환자용 오늘 콘텐츠
- `apps/mobile` 환자용 기록 및 회고 흐름
- `apps/mobile` 환자용 마이페이지
- `apps/web` 모바일 웹 화면의 구조 미러링

제외:

- `apps/web` 관리자 화면
- 백엔드 스키마 대규모 변경
- 관리자용 운영 흐름 재설계

## 핵심 원칙

1. 디자인과 경험의 기준 원본은 모바일 앱이다.
2. 웹 모바일은 모바일의 정보 구조와 UX 흐름을 미러링한다.
3. Figma 경험을 우선한다.
4. 기존 데이터 구조와 정확히 맞지 않는 부분은 가공값, 임시 문구, 기본 상태를 사용해 화면 경험을 먼저 맞춘다.
5. 기존 세션, API, 포트 계층은 최대한 유지한다.
6. 모바일 UI는 반드시 기존 디자인 시스템 토큰과 공통 컴포넌트를 사용한다.

## 추천 접근

세 가지 접근 중 `환자 경험 레이어 재구성` 방식을 채택한다.

- 단순 화면 갈아끼우기는 빠르지만 공통 규칙이 약해지고 웹 미러링 비용이 커진다.
- 모바일과 웹을 동시에 재구성하는 방식은 현재 우선순위와 맞지 않는다.
- 따라서 모바일에서 환자용 공통 셸, 하단 내비게이션, 홈 히어로, 일일 흐름, 대화 허브를 먼저 재정의한 뒤 각 화면을 그 위에 배치하는 방식이 가장 적합하다.

## 목표 구조

모바일 환자 영역은 다음 다섯 흐름으로 재구성한다.

1. 홈
2. 오늘,우리
3. 오늘 콘텐츠
4. 기록 및 회고
5. 마이페이지

기존의 `HomeScreen`, `ChatScreen`, `ContentListScreen`, `ProfileScreen`은 현재 책임을 유지하지 않는다. 라우팅 엔트리와 데이터 연결은 활용할 수 있지만, 화면 책임과 정보 위계는 Figma 기준으로 다시 정의한다.

## 화면 구조 설계

### 1. 홈

홈은 정보 카드 묶음이 아니라 정서적 시작 화면이어야 한다.

구성:

- 현재 날짜 노출
- 태명 또는 아기 호칭 강조
- 아기의 한마디 말풍선
- 임신 진행 정보와 남은 일수
- 오늘 흐름으로 진입하는 행동 유도

설계 의도:

- 사용자가 앱을 열었을 때 가장 먼저 감정적 연결을 느끼게 한다.
- 기존의 기능 요약 중심 홈을 버리고, Figma `NewHome`의 감성적 히어로 구조를 기준으로 삼는다.
- 일정, 기록, 콘텐츠는 홈에서 모두 직접 펼치지 않고 다음 흐름으로 연결한다.

### 2. 오늘,우리

오늘,우리는 단순 채팅 화면이 아니라 하루 허브다.

한 화면 안에서 다음을 묶는다.

- 오늘 아기는요
- 오늘 엄마는요
- 함께 해봐요
- 아기와 나누는 마음

설계 의도:

- 콘텐츠, 체크리스트, 감정 표현, 채팅을 분산시키지 않고 한 흐름으로 모은다.
- 현재의 채팅 화면 단일 책임을 버리고, Figma `Conversation`의 일일 허브 구조를 모바일 앱 핵심 경험으로 승격한다.
- 모바일에서는 세그먼트나 탭 전환으로 묶되, 사용자가 다른 화면으로 튀는 느낌을 최소화한다.

### 3. 오늘 콘텐츠

오늘 콘텐츠는 홈과 오늘,우리에서 파생되는 상세 화면으로 둔다.

구성:

- 하루 또는 주차 기반 설명 확장
- 아기 변화와 엄마 변화의 세부 정보
- 행동 권장과 주의 포인트

설계 의도:

- 메인 허브에서 모든 설명을 다 담지 않고, 필요 시 더 깊게 읽을 수 있는 상세 화면으로 분리한다.

### 4. 기록 및 회고

기록과 회고는 결과를 남기는 흐름으로 둔다.

구성:

- 날짜별 기록 진입
- 감정 또는 회고 문장 저장
- 오늘 대화와 연결된 회고 맥락

설계 의도:

- 기존 달력 기록 접근성을 유지하되, 홈의 핵심 역할로 두지는 않는다.
- 사용자는 감정적 진입 후 대화와 실천을 거쳐 기록에 도달해야 한다.

### 5. 마이페이지

마이페이지는 우선순위가 가장 낮지만 하단 내비의 한 축으로 유지한다.

구성:

- 기본 프로필
- 임신 정보
- 앱 설정 또는 안내

설계 의도:

- 전체 흐름 재편에서 부차적 영역으로 두되, 하단 내비 구조의 완결성을 유지한다.

## 내비게이션 설계

모바일 환자 내비게이션은 Figma의 사용자 앱 구조를 참고해 재정의한다.

기본 원칙:

- 하단 내비는 환자 흐름 중심으로 단순화한다.
- 홈, 오늘,우리, 마이페이지는 고정 축으로 유지한다.
- 오늘 콘텐츠와 기록/회고는 허브에서 파생되는 상세 흐름으로 둔다.

의도:

- 기존에 기능별로 흩어진 이동 경로를 줄이고, 하루 단위 경험을 중심에 둔다.

## 데이터 및 상태 설계

### 데이터 우선순위

데이터 정확도보다 Figma 경험을 우선한다.

의미:

- 현재 API에서 바로 주지 않는 값은 화면 전용 표시 모델에서 가공한다.
- 값이 없으면 임시 문구, 기본 상태, 파생 계산값으로 채운다.
- 백엔드를 기다리지 않고 클라이언트에서 먼저 경험을 완성한다.

### 모바일 표시 모델

기존 포트를 그대로 노출하지 않고 화면 전용 표시 모델로 재조합한다.

예시:

- 홈 전용 모델: 날짜, 태명, 아기 메시지, D-day, 주차, 감성 문구, 진입 행동
- 오늘,우리 모델: 아기 정보, 엄마 정보, 체크리스트, 회고, 채팅 입력 상태
- 기록 모델: 날짜 목록, 감정 요약, 회고 진입 상태

### 저장 전략

- 체크리스트, 회고, 채팅은 내부적으로 기존 API 또는 스토리지 포트에 분배 저장한다.
- 화면에서는 하나의 일일 흐름처럼 보이되, 저장은 기존 경로를 최대한 유지한다.

## 모바일 구현 경계

다음 경계로 나눈다.

1. 환자용 공통 셸 및 하단 내비 재정의
2. 홈 재구축
3. 오늘,우리 허브 재구축
4. 오늘 콘텐츠 재구축
5. 기록 및 회고 재구축
6. 마이페이지 재구축

공통 컴포넌트 원칙:

- `src/tokens.ts`, `src/theme.ts` 기준 유지
- `Card`, `Button`, `HeroSection`, `EmptyState`, `KeyboardScreen`, `Pressable` 우선 사용
- 매직 넘버, 로컬 그림자, 직접 RN `Pressable` 남용 금지

## 웹 미러링 설계

`apps/web`의 모바일 웹은 모바일 앱 구조를 미러링한다.

원칙:

- 화면 순서와 정보 위계는 모바일과 같아야 한다.
- 웹이 별도 UX 원본이 되지 않는다.
- 가능하면 모바일과 같은 표시 모델 이름과 섹션 순서를 유지한다.
- 차이는 렌더링 기술과 상호작용 제약에 한정한다.

이 설계는 이후 웹 작업을 모바일 결정의 번역 작업으로 축소시키는 것이 목적이다.

## 오류 처리

- 데이터가 비어 있어도 화면은 비어 보이지 않아야 한다.
- 환자용 문구는 따뜻한 톤 `-어요/-해요` 체를 유지한다.
- 실패 시에도 Figma 구조를 깨지 않는 기본 상태를 제공한다.

예:

- 아기 메시지 없음 → 기본 감성 문구 표시
- 체크리스트 없음 → 비어 있음 안내 대신 오늘 해볼 만한 기본 안내 제공
- 채팅 불러오기 실패 → 대화 유도 시작 상태 유지

## 테스트 전략

### 모바일

- 환자용 핵심 화면 스냅샷 또는 구조 테스트
- 홈 표시 모델 변환 테스트
- 오늘,우리 허브 상태 조합 테스트
- 기존 세션 및 데이터 로딩 회귀 점검

### 웹

- 모바일 웹 화면 구조 테스트
- 모바일과 동일한 섹션 순서 및 핵심 문구 검증

## 리스크

1. Figma Make의 일부 표현이 현재 데이터 모델과 직접 연결되지 않을 수 있다.
2. 기존 라우팅 구조가 새 정보 구조와 충돌할 수 있다.
3. 홈과 오늘,우리 사이의 책임 분리가 불명확하면 다시 화면이 비대해질 수 있다.
4. 모바일과 웹을 동시에 맞추는 과정에서 웹이 독자 구조로 새기 시작할 위험이 있다.

## 리스크 완화

- 먼저 모바일 구조를 확정하고 웹은 후행 구현으로 둔다.
- 화면 전용 표시 모델을 둬 데이터 결핍을 흡수한다.
- 오늘,우리 허브에 들어갈 책임을 명시적으로 제한한다.
- 테스트는 공통 섹션 순서와 핵심 문구, 진입 경로 중심으로 둔다.

## 구현 순서

1. 모바일 환자 셸과 하단 내비 재정의
2. 홈 화면을 Figma 기준으로 재구축
3. 오늘,우리 허브를 구성하고 정보/체크리스트/대화 통합
4. 오늘 콘텐츠, 기록/회고, 마이페이지를 같은 디자인 언어로 재편
5. 웹 모바일 화면을 모바일 구조 기준으로 미러링

## 완료 기준

- 모바일 환자용 핵심 흐름이 Figma 기준 구조로 재편되어야 한다.
- 웹 모바일 화면이 모바일 구조를 미러링해야 한다.
- 기존 세션 및 API 연결이 유지되어야 한다.
- 데이터 공백이 있어도 화면 경험이 깨지지 않아야 한다.
